## 0. 什么叫「上一个档次」

先立判断标准，避免把升级做成堆料。一个候选设计进入本方案，必须同时过三关：

1. **语义绑定关**：新元素必须绑定流水线的真实语义，由类型化事件驱动。
   装饰性的热闹（更多手势、更多家具）一律不进。
2. **闭环关**：要么让用户多看见一层真实状态，要么让看见多转化一种行动。
   只出不进或只进不出的都是半成品。
3. **可检验关**：说得出它改善哪个测量指标（SA L1/L2/L3、错误发现延迟、
   信任校准、干预粒度），将来实验能证伪。

以下五个支柱都过了三关。反例也留一条：给角色加「经验值/升级系统」曾在候选里，
因为找不到对应的真实语义（LLM 不会因为跑了十单而变强）被砍掉——它违反第一关，
且正好踩中拟人化误导信任的雷（论文 §2.5 的 HATEM 反论）。

## 1. 现状盘点：v20 的五个结构性天花板

v20 之后，Claw 已具备：6 阶段流水线、8 角色注册表、5 种 claw.* 事件、办公室
tick 引擎、拖拽派活、拍拍肩问进度、L3 排程投影、运行时改绑。但有五个问题是
结构性的，加功能绕不过去：

| # | 天花板 | 表现 | 后果 |
|---|---|---|---|
| T1 | 空间仍是半只读 | 只有产物能拖、只有小人能点；任务卡、白板、会议室、房间本身都是布景 | 干预面窄，DG4 只兑现了一小半 |
| T2 | 办公室只有现在时 | 事件流过即弃，回放靠翻聊天记录；「昨天那单是怎么错的」无法重看 | 复盘、审计、实验（录制回放）都缺基础 |
| T3 | 场景语法报喜不报忧 | 成功有 eureka/庆祝/敲钟三连，失败只有捂脸+锤人喜剧化处理；返工、部分失败、低质量产物没有视觉语法 | 正是误导信任的形状：界面系统性放大好消息。HATEM 风险不是理论,是我们自己造的 |
| T4 | 舞台随运行生灭 | 一个 URL = 一次运行 = 一间办公室；关掉即散伙 | 与「AI 员工团队」的核心隐喻矛盾——员工不该每单重新入职 |
| T5 | 绑定是习惯不是规范 | 事件→场景的映射散落在 ClawOffice/officeSim 的 if-else 里；会议靠「critic 有 tool 事件」这类推断 | 不可迁移、不可配置、论文声称的「绑定表方法论」在代码里找不到对应物 |

## 2. 北极星

**办公室是界面，工作室是产品。** 用户与 Claw 的关系从「发任务、看动画、拿
产物」升级为「经营一支常驻的 AI 团队」：团队有可查的履历与账本，工作室有
可回放的历史与可预期的日程，空间里的每个名词都可以被操作，而且这间办公室
说真话——干得差的时候看起来就是干得差。

五个支柱各打穿一个天花板。

## 3. 支柱一：场景语法 v2 —— 把绑定表变成数据（打 T5）

### 3.1 设计

论文 §3.3 的核心主张是「场景语法与流水线语义绑定」，但代码里绑定是隐式的。
升级：把绑定表提升为一份**声明式规范**，运行时按规范驱动场景。

```
apps/web/components/claw/sceneGrammar.ts   （新，数据文件）
  SCENE_GRAMMAR: Array<{
    when:   EventMatcher      // { kind: "claw.plan" } / { kind: "tool.end", agent: "critic", error: true } …
    stage:  SceneDirective    // { scene: "meeting", kind: "kickoff" } / { actor: "$agent", gesture: "facepalm" } …
    sa:     "L1" | "L2" | "L3"  // 该条绑定服务哪个 SA 层（自文档化）
    priority: number          // 冲突时的裁决序（meeting > reaction > ambient）
  }>
```

officeSim/ClawOffice 里现存的 if-else 逐条搬进规范；引擎归约为一个解释器：
事件进来 → 匹配规则 → 产出舞台指令。氛围行为（闲逛/串门/咖啡）不在规范里，
它们是缺省态，规范只管语义事件。

### 3.2 为什么这是档次而不是重构洁癖

- **协议补齐**：现在「评审会」靠推断（critic 的 tool 事件活跃）。后端补发
  一等公民的阶段事件 `claw.phase`（payload: phase, status: start/end），
  规划/辩论/执行/撰稿/评审/制片六个阶段显式开闭。推断降级为兜底。这一条
  同时修掉一类真实 bug：推断制造的会议时长与真实评审时长对不上。
- **可配置与可迁移**：绑定表成为数据之后，「隐喻包」成为可能——同一份事件
  协议可以换一套 grammar 渲染成厨房（出餐口=交付）或片场（打板=阶段切换）。
  近期不做第二个包，但论文的「绑定表方法适用于任何类型化事件流水线」主张
  从此有代码实体可指。
- **实验条件的实现基础**：三视图信息等价（§7）要求三种表征消费同一事件流。
  grammar 解释器就是办公室这一路的消费端，清单/日志视图是另外两个消费端，
  同源不同渲染,信息等价由架构保证。

### 3.3 验收

- `SCENE_GRAMMAR` 单文件覆盖现有全部语义绑定，ClawOffice 内语义 if-else 清零；
- 后端 `claw.phase` 事件上线，评审会时长与真实评审耗时误差 < 1s；
- 论文 §3.3 的绑定表与代码规范逐行对得上（文档即测试）。

## 4. 支柱二：诚实的办公室 —— 失败与不确定性的场景语法（打 T3）

### 4.1 设计立场

这是五个支柱里最重要的一个。当前语法在庆祝成功上花了三种仪式，在暴露问题上
只有喜剧化的捂脸。如果 HATEM 的预测成立（拟人化让用户该撤信任时不撤），
Claw 现在的设计是在帮倒忙。升级方向：**让坏消息获得与好消息对等的舞台权重**，
且全部用可观察代理，不让模型自报信心（模型的自信不可信，这类信号一律不用）。

### 4.2 机制

| 机制 | 触发（可观察代理） | 舞台表现 | 服务指标 |
|---|---|---|---|
| 返工循环可视 | 同一角色对同一任务的第 2+ 次工具调用（重试计数） | 工位上方 ↻×n 徽标；小人挠头姿态替换正常工作手势 | 错误发现延迟 |
| 质检章 | critic 复审产出 v2 时,diff 出被修改的段落数 | 评审会结束时报告封面盖「改 n 处」红章;n=0 盖绿章「通过」 | 信任校准（评审不是橡皮图章的证据） |
| 问题墙 | tool.end error、超时、降级(角色被跳过) 的累积 | 办公室一面墙的「事故板」逐条钉上便签,点击下钻到原始事件 | SA L2、审计 |
| 半成品姿态 | 收尾守卫补记的 done(非正常完成)、软失败保留 v1 | 交付庆祝降级:不敲钟,调度员说明「这单有 n 处凑合」 | 信任校准（庆祝分级） |
| 弃权可视 | 澄清门放行但置信低（三元判断的"失败=放行"分支） | 调度员开工时嘀咕「没太看懂,先按我的理解干了」 | 过度信任的最脆弱点（He et al. 的发现就在这里） |

关键决策：**庆祝分级**。敲钟+全员派对只留给零事故、零返工、评审绿章的运行；
有瑕疵的交付降为普通下班。当前版本一律敲钟，这是把仪式感放在忠实性前面，
v2 反过来。

后端配套：`claw.artifact.updated` 增加 `issues` 字段（critic 修改数、守卫
补记数）；`tool.end` 已带 error，无需改。

### 4.3 验收

- 错误注入运行（预置一次检索失败 + 一次评审改 3 处）下，问题墙 2 条、
  返工徽标出现、红章「改 3 处」、不敲钟；
- 正常运行仪式不变（回归）；
- 论文 §7 的 H3-benefit 从「设计论证」升级为「已实现机制」,实验直接可跑。

## 5. 支柱三：全可操作空间 —— 名词皆可动（打 T1）

### 5.1 设计

v20 打通了产物→小人的拖拽。补齐剩下的名词，原则不变：每个空间操作翻译成
一条真实的系统动作（追问轮 / plan 补丁 / 配置变更），不做纯前端戏法。

| 操作 | 空间手势 | 系统动作 | 依赖 |
|---|---|---|---|
| 改派任务 | 从计划卡拖任务行到另一个小人身上 | 新 API `PATCH /claw/{id}/plan`:改该 task 的 role(仅 pending 任务、仅 finished/awaiting 时);下一轮执行按新派工走 | 后端(小) |
| 召集商议 | 把小人 A 拖到小人 B 身上 | 追问轮:「让{A}和{B}就当前方案对一轮意见」→ 复用辩论机制的双角色变体 | 后端(中,debate 子集) |
| 白板即 brief | 点会议室白板 → 编辑面板 | 白板内容 = 澄清 brief + 辩论共识(已有数据);编辑后作为追问轮提交「按修改后的要求调整」 | 前端为主 |
| 传阅产物 | 报告拖到评审员身上 | 追问轮:「让评审员再复审一遍报告」(现有 critic 通道) | 前端 |
| 房间门禁 | 拖某小人到「休息区」并按住 | 等价于绑定面板停用该角色(下一轮生效),松手弹确认 | 前端(复用 PUT /claw/roles) |

改派任务是唯一需要新后端能力的（plan 补丁），也是价值最高的：它把「团队
构成控制」从工具粒度（改绑）推进到任务粒度，正好填满论文 §2.4(c) 空位的
另一半。约束从简：只允许动 pending 任务、只在非 running 状态、role 必须
enabled 且工具匹配——校验失败时小人摆手拒收（拒收本身也是诚实语法）。

### 5.2 验收

- 五个操作各自触发正确的系统动作且可从事件流验证（不是动画）；
- 非法改派（角色停用/工具不符/任务已 doing）被拒且有空间反馈；
- 键盘/点击路径保留等价操作（可达性：拖拽不是唯一入口）。

## 6. 支柱四：时间轴 —— 记录、回放、日程（打 T2）

### 6.1 设计

事件流本就经过 `/api/v1/sessions/{id}/events` 的 `/log` 回放端点（v1 设计
遗产），但从未产品化。升级成三件套：

1. **事件日志落库**：`claw_events` 表（run_id, seq, ts, kind, payload jsonb），
   运行中顺写。这是回放、审计、实验录制回放共用的唯一数据源。
2. **时光机**：办公室左下角加时间轴滑块。拖动 = 把 grammar 解释器喂历史
   事件重演场景（解释器是纯函数（事件序列→舞台状态），支柱一做完这里就
   便宜了）。倍速 1×/8×/32×，事故点在轴上标红。
3. **日程板**：把 L3 从「下一步」延伸到「整单预期」——例会结束时墙上的
   日程板列出阶段序列与粗估耗时（估计值来自历史同类运行的统计，不是模型
   自报），实际进度在板上打点。估计与实际的偏差本身可视——又一条诚实语法。

### 6.2 实验红利

论文 §7.3 的录制回放法在这里变成产品能力：同一份 `claw_events` 序列可以
喂给办公室/清单/日志三种视图，跨条件跨参与者完全一致。实验基建与产品功能
第一次是同一份代码。

### 6.3 验收

- 任一 finished 运行可离线重演，重演结果与当时的 live 场景一致（用支柱一
  的解释器纯函数性质做快照测试）；
- 时间轴红点数 = 问题墙条目数（同源校验）；
- 日程板估计耗时来自 ≥3 次历史运行的中位数，样本不足时显示「首单,没谱」
  而不是编一个数。

## 7. 支柱五：常驻工作室 —— 跨运行的持续性（打 T4）

### 7.1 设计

`/claw` 从「新建任务页」升级为**工作室首页**：一间常驻办公室，历史运行是
桌上的案卷（点开进入该 run 的时光机/产物），新任务从前台派入。角色获得
跨运行的**履历卡**（dossier），替换现在冷加载后归零的统计：

- 履历数据全部来自 `claw_events` 聚合：接单数、工具调用数、成功率、返工率、
  平均耗时、经手产物列表、被评审改动的历史曲线；
- 履历是**账本不是等级**——没有经验值、没有升级、没有技能树（§0 的反例）。
  设计师的履历显示「32 张图、返工率 8%」，这是可核查的事实陈述；
- 改绑/停用历史也入履历（「上月 web_search 曾改派给工程师 3 天」），团队
  构成的变更第一次可追溯。

这一支柱同时是 Claw Desktop 产品方向（常驻桌面 AI 团队）的 Web 端预演：
工作室壳先在 Web 里养熟，桌面化时整体平移。

### 7.2 验收

- 关浏览器重开，工作室与全部历史案卷仍在（DB 水合，匿名用户降级为单次）；
- 履历卡每个数字可点击下钻到产生它的事件集合；
- 新任务的日程板估计（支柱四）引用的正是履历统计——两个支柱共享同一账本。

## 8. 横切：三视图信息等价

办公室右上角加视图切换：**办公室 / 清单 / 日志**。三者消费同一事件流
（支柱一的架构保证），信息等价、仅表征不同。

产品价值：这就是 catch-22 的完整答案——缺省给隐喻（可理解），存疑给日志
（细节完备），两键切换。论文价值：实验条件 A/B/C 不再是为实验搭的假界面，
是产品本身的三档；「三条件信息等价」从实验设计声明变成可审计的代码事实。
成本很低：清单视图 ≈ 现有 TaskPlanCard + 阶段时间线的组合，日志视图 ≈
ToolStrip 的全量版。

## 9. 里程碑

每个独立可验收，按依赖排序；V21/V22 合起来就是论文实验的全部系统前置。

| 里程碑 | 内容 | 主要风险 |
|---|---|---|
| **V21 语法即数据** | 支柱一：SCENE_GRAMMAR + 解释器重构 + 后端 claw.phase 事件 | 重构回归——用现有 stub 路由做场景快照对比 |
| **V22 诚实语法** | 支柱二全部 + 三视图（横切） | 「不敲钟」可能被觉得扫兴——庆祝分级放一个配置开关,默认诚实 |
| **V23 名词皆可动** | 支柱三：plan 补丁 API + 改派/商议/白板/门禁 | PATCH plan 的并发语义(与 running 状态互斥即可) |
| **V24 时光机** | 支柱四：claw_events 表 + 回放滑块 + 日程板 | 事件量级(单 run 数百条,无压力);重演一致性靠 V21 的纯函数 |
| **V25 工作室** | 支柱五：工作室首页 + 履历卡 + 案卷 | 信息架构改动大,单独出一版 UI 方案再动手 |

预估：V21–V22 是主体（前端重构 + 少量后端事件），V23 后端小改，V24 一张表
一个滑块，V25 是独立的产品迭代。V21–V24 全部落在现有技术栈内，无新依赖。

## 9.5 V26 能力全接入（Dream-Waver → Claw）

用户方向：把 Dream-Waver 的全部纵切能力接进 Claw，让工作室成为所有能力的
前门。原则：**拿能力不拿界面**——每个纵切以工具适配器进角色注册表（
generate_deck 走 slides 管线是现成范式），不搬各纵切的 UI。

盘点结论（2026-07-02 审计，43 项未接线，按批次排序）：

| 批次 | 能力 | 数量 | 接法 | 状态 |
|---|---|---|---|---|
| 批一 | design 变体 generate_variants | 1 | designer 新工具,bridge.GenerateVariants 适配器 | **已落地** |
| 批一(核实为已有) | outpaint / img2img | 2 | edit_image 的 op 枚举早已覆盖(审计误报) | 已有 |
| 批二 | games 纵切 generate_game | 2 | 新「游戏制作人」角色或制片扩权;games.Pipeline.Run 适配器;需要 claw session 新增 game 产物槽(迁移+快照+前端 tab)——工作量在产物通道不在工具 | 方案 |
| 批三 | slides 编辑工具(高频 6-8 个: 改文字/换主题/加删页/重排/评审 deck) | ~30 中选 8 | 作用于 deck 的 slides session(Deck.PreviewID 已在);制片获得"出片后继续改"闭环;每工具一薄适配器 | 方案 |
| 批四 | video bridge 时间线迭代(CreateRun/Regen/Timeline) | 5 | 视频师从单发 i2v 升级为可迭代短片 | **暂缓**(见下) |

claw 只存引用。批三未逐个搬工具，而是 edit_deck 委托给 slides
AgentRunner.Continue，一个工具白拿全部 ~20 个 slides 编辑能力。

## 11. 风险与对策

| 风险 | 对策 |
|---|---|
| 诚实语法伤害「爽感」,用户流失 | 分级而非取消庆祝;错误表现保持像素幽默感(挠头/便签墙),诚实 ≠ 阴沉 |
